# 卡牌设计转译与引擎执行的两阶段验收

本方案承接 [Issue 44](https://github.com/Time-Block-Hero/time-block-hero-unified/issues/44)。用户要求固定当前网页卡牌和三项通用规则，并将卡牌验收分成两个独立可审阅的步骤。本文件定义验收边界，不宣称新的表达式或引擎行为已经实现。

## 固定输入与当前范围

2026-09-20 的设计基线保存在本提交的 `data/cards.json`；`data/baselines/issue44-20260920/revision.json` 记录原始字节摘要、基线来源、逐 UID 删除与字段差异。共132张：删除5张中立不可收集卡，21张职业卡文修改，5张剩余中立不可收集卡仅编号重排。36张中立可收集卡文未改。

卡牌身份按UID追踪，不能用重排后的展示编号猜测替代关系。删除保留退役事实，旧已发布快照不覆盖。工作编辑器可继续修改；以后编辑构成新版本，不改变本次提交及其摘要。冻结设计只固定输入，不表示所有职业卡、衍生卡或排除设计已经被验收。

规则基线采用本提交 `docs/rules/` 的规范正文及来源记录。分配先选完、后同批结算；玩家慢速入场准备当场完成、正文时停末执行；效果保留一次实际加计数并触发保留后续。卡文明示的随机选取在正文执行时才查询合法候选并取样：慢速在时停末轮到其执行时，快速在当次正文中；因此可包含对手本轮新放置且届时仍合法的单位。此边界已由用户明确确认。

本轮执行验收范围继续为36张中立可收集卡；职业和中立不可收集卡保持暂停。保存职业改稿不构成恢复职业测试的指令。规则变化会使旧39项测试结论只适用于旧基线，需要分析新规则的影响后重新验收。游戏生产卡库目前仍是旧133张候选，尚未将本次删除/改稿导入。

## 第一步：卡文与规则 → 执行说明 → 作者 JSON

归属：设计与规则源在 tbh-website；自然语言执行说明、逐句映射和可执行作者 JSON 在 tbh-rules-engine 的 `Authoring~/Authoring`（现有 v1/cards/<uid>.card.json）。编译器在 `Tools~/Content`，产物在 `Runtime/Resources/TimeBlockRules/GameContent`。tbh-assets 继续只管理插画、卡框、资源映射及 Unity GUID；本方案不移动仓库职责。

每张卡都形成可独立审阅的说明，至少包括：

- UID、卡文原文与摘要、规则版本及所引用的规范条款。
- 生效区域、触发条件、效果速度；准备阶段选择哪些目标、模式、数量、方向或分配。
- 选择合法性、是否可重复、随机方法；必须支付的成本与次数。
- 哪些对象/数值在准备时锁定，哪些在执行时读取；任何尚未确定的时点显式标记未完成。
- 正文操作顺序、同批边界、状态变化、产生的事实与后续触发。
- 目标失效、数量不足、取消、来源离场和部分完成的规则依据。
- 将以上说明映射到作者 JSON 的具体 Plan、查询、操作与参数；不支持的通用语义标为缺口，不使用空 Plan 或逐卡硬编码伪装完成。

例如“入场：将3点护甲分配给友方随从”：成功入场后查询合法友方随从，选择总计3点，允许 A 两点、B 一点；提交后保存分配与目标入场身份；时停末重检各目标，对仍合法者在同批分别赋予2和1护甲。中途不先给 A 加1点，不重新分配失效目标的份额。若为快速入场，该正文在当次准备完成后执行。该示例为自然语言说明，不冒充已经编译完成的 JSON。

验收 A：逐句卡文与规则能解释每一个语义决定；说明与 JSON 一致；schema/编译及引用完整性通过；保留退役UID与引用迁移清单。需要新增操作的卡只能标为“说明已审阅、表达式待支持”，不能算整步通过。人的语义审阅不可被编译器通过替代，也不承诺从任意中文自动可靠地生成 JSON。

## 第二步：作者 JSON → 通用引擎执行

输入为第一步固定摘要的表达式及其预期行为。引擎只实现可复用的查询、选择、批量变化、事件和阶段规则，不按中文卡名或展示编号打补丁。

验收 B 使用独立写出的初始局面、输入/随机序列和预期结果，对实际生产 Loader、执行器与结算内核运行：

- 分配：玩家点选和窗口外自动代选均满足总量、重复目标、逐点等概率取样；显式随机与自动代选具有同样语义。固定序列 A、A、B 产生 A=2、B=1，全部选完前没有结算副作用；统一批量死亡、护甲及后续边界。测试分配与“逐次造成伤害”有可观察区别。
- 入场：慢速当场完成准备并可读出待结算信息，时停末只执行已登记正文；快速当次选择并执行；目标离场再入场不恢复原锁定；失效不改选。随机选取应包含对手本轮新放置且届时仍合法的目标，并排除此前已失效的目标，不能提前缓存放置时的候选名单。依赖正文新结果的选择保留相应执行步骤。
- 保留：通用合成卡执行真实保留后先增加计数再产生一次保留事件；同回合执行两次增加2并各触发一次，随后自然回合末保留仍可增加1。仅“视作＋2”不产生事件；不推进回合、不执行整轮清理、不凭空授予保留词条。当前用合成夹具验证通则，不恢复烈阳职业卡测试。
- 确定性：同一输入与随机序列得到相同结果/事件顺序；重复输入不重复支付或触发。

两个回执分别报告 A、B，绑定同一套卡文、规则、执行说明与 JSON 摘要。B通过不能证明A正确；A通过也不能证明B正确。另保留“真实卡牌端到端”结果，确认两个步骤接合，但不将其混写成单一Implemented标签。

## 后续实施拆分与已知缺口

1. **固定输入（本变更）**：保存当前设计、三条规则、历史差异和双阶段标准；不改运行效果。提交网站 PR，保留用户编辑工作区。
2. **A：36张中立说明与表达式复核**：为每张建立规则引用、执行步骤与JSON映射，按新基线报告通过/缺口；对删除的5张仅记录未来导入的显式退役与引用处理，不恢复衍生效果测试。
3. **B：公共机制修正**：统一显式随机和窗口外自动分配；删除旧随机伤害逐点立即结算路径；独立实际保留操作共用加计数/事件语义，回合末去重只归回合末调度。用通用合成例验证机制，不靠职业卡验收补覆盖。
4. **A/B 联合中立复验**：运行新基线的36张真实卡牌与必要边界，分别出具两个阶段结果；维护原规则/内容 PR。职业卡待逐职业确认后开展同样流程。
5. **后续集成**：固定可获取候选SHA，与统一工程 manifest/lock/兼容矩阵对齐，按既有流程验收 Unity；不把 .NET 单层通过称作完整 Unity/Full/Windows 通过。

现有代码差距已只读定位：窗口外 PlayerSelect Allocation 与显式 RandomSelect Allocation 的概率算法不同；RandomDamage 仍逐点结算；真实保留只在回合末路径产生，恩典旧作者表达式仍是读值 modifier。当前纯设计提交导出还要求原137UID齐全，132张冻结数据尚不能通过该旧生产导出入口；导入前须按本次5张显式退役记录扩展身份版本合同，不能关闭缺失UID校验或偷偷恢复已删卡。

仓库、schema及引擎迁移的具体实现沿用现有Issue/PR，不另建重复总任务。合并、发布和Issue关闭仍由用户/审阅者决定。回滚时使用前一固定设计、规则及对应内容候选的完整组合，不混用不同版本的卡文与表达式。
